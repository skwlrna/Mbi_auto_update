# 18단계 — 공통 오류 감지 기반 및 AI 오류 진단 연결

## 목적과 범위

이미 해결된 **밥 제작 누락 문제는 이번 단계 범위에 포함하지 않는다.**
기존 모비매크로에는 채집·가공·제작·낚시·던전·어비스·스케줄러 등
각기 다른 자동화 기능이 있으며, 오류 보고 시 독립적인 경로와
검증 수준이 섞이면 원인을 확정했다고 오인할 수 있다.

이번 단계의 구현 대상은 **자동화 전체 기능을 위한 공통 오류
진단 분류 모델과 기존 AI 오류 기록의 수동/옵트인 연결**이다.
기존 사용자 입력, 매크로 시작/중지, 완료 판정, 안전 정지, AI 코드
수정·테스트·검토·롤백을 **변경하지 않는다**.

## 실제 구현

- `source/FishingAutomation/Telemetry/CommonIncidentTriage.cs`:
  UI가 이미 사용하던 정확한 모드 레이블만 받아 아래 진단 범주에
  대응한다. 임의의 오류 제목·상세 문구·캐릭터명·레시피·아이템 이름을
  분류에 직접 사용하지 않는다.
- `AiPassiveCliEvidence.SnapshotForIncident`:
  AI 감시기가 사용자가 허용한 상태일 때만, **기존에 끝난**
  읽기 전용 CLI 상태 중 오류 발생 시각 **이전 5초** 이내의
  허용된 결과를 최대 5개 참조한다. 조회를 새로 실행하지 않는다.
- `AiRuntimeErrorJournal.Record`: 기존 `error.txt`에
  `BEGIN COMMON INCIDENT TRIAGE V1` / `END COMMON INCIDENT TRIAGE V1`
  사이의 **고정된 영역·관측 범위·가설·연결 단서**를 별도 블록으로
  추가한다. 기존 AI 감시기는 이 자료를 이전과 같이 **비신뢰 로그
  데이터**로 읽으며, 이를 조작/코드 수정/운영 배포 승인으로
  승격시키지 않는다.
- `ai-autopilot/evidence_ab.py`: 14–15단계의 동일 오류 전후 비교가
  새 18단계 진단 블록 때문에 편향되지 않도록, 엄격히 확인된
  **두 종류 진단 블록을 모두 제거한 자료**를 비교의 Before 기준으로
  사용한다. 임의의 `repair_authorized=true`, 미승인 버전·개인정보·
  중복 블록은 유효한 증거로 인정하지 않는다.

## 기능별 근거 범위

| 매크로 기능 | 현재 오류 진단에서 쓸 수 있는 단서 | **아직 검증되지 않은 내용** |
|---|---|---|
| 채집 | 기존 읽기 전용 `get_activity`의 채집 진행 표식 | 채집 성공, 수령/인벤토리 변화, 수집 완료 |
| 가공/다중가공 | 기존 `get_altering_works`의 진행·완료표시·빈 목록 및 17단계 집계 변화 | 개별 작업 ID, 실제 취소 이벤트, 결과물 수령 |
| 제작 | 모드 구분 가능 | 실시간 제작 성공·부족 재료·완료 신호 |
| 낚시 | 모드 구분 가능 | 입질·위치·보상 이벤트 |
| 일반 던전·페카 심층·어비스 | 모드 구분 가능 | 방 전환·기믹·클리어 확증 |
| 스케줄러 | 모드 구분 가능 | 오류 시각의 검증된 실행 단계·서버 작업 확증 |

모든 모드에는 추가로 **CLI 연결 조회 실패/시간 초과 등**을
'연결 관련 단서'로 별도 기록할 수 있다. 그러나 연결 실패가
해당 모드의 오류 **원인이라고 확정하지 않는다**. 단순 연결
성공 또한 게임 행동 성공 근거가 아니다.

## 안전성 및 한계

- 새 CLI 조회, 화면/OCR 추가 실행, 패킷 복호화, 패킷 수집,
  주기적 백그라운드 폴링, 매크로 키 입력, 자동 수정·재시도 없음.
- 정해진 분류 레이블만 사용. 매크로 오류 제목, CLI 원문,
  캐릭터 이름, 원본 아이템·레시피 정보, 개인 키·주소를 새
  진단 블록에 넣지 않는다. (기존 오류 보고서 다른 필드의
  개인정보 처리 정책은 이 변경과 별개이다.)
- **검증된 원인, 게임 조작 허가, AI 수정 허가가 모두 false**로
  고정된다. `mode`는 매크로가 로컬에서 선택한 모드일 뿐
  실시간 게임 상태를 보증하지 않는다.
- 독립적인 화면/OCR 값과 동일한 CLI 상태를 상호 검증하는
  **실시간 교차검증 연결은 아직 하지 않았다**. 화면·패킷에서
  검증되지 않은 데이터를 '독립적인 2차 근거'로 사용하는 것은 금지한다.
- 개발 PR #231만 업데이트했으며, main·운영 매크로와
  기존 테스트 ZIP은 자동으로 갱신되지 않는다.

## 검증

합성 테스트에서는 실 UI의 모든 모드 레이블과 알 수 없는 모드,
가공 제거 가능성·채집 진행 표식, 다른 모드의 CLI 결과
오판 방지, 5초 만료·오류 이후 관측값 제외, AI 감시기 종료 시
메모리 폐기, 개인 식별정보 비노출, 조작/수정 허가 불가를 검사한다.

Python A/B 테스트에서는 새 블록을 함께 제거한 동일한 원본 오류가
비교의 Before가 되는지, 임의의 승인값을 차단하는지 확인한다.
기존 Windows 빌드, 어비스·가공 스케줄러, 생산 엔진 회귀 검사도 유지한다.

**여전히 입증되지 않은 것:** 실제 게임에서 오류율 감소, AI가
원인을 더 정확하게 찾는 비율, Codex 복구 성공률, 화면/CLI 신호
일치율, 패킷의 이벤트 의미. 해당 수치는 독립적인 실측 근거가
있을 때만 평가한다.

다음 순서는 **기존 화면 판정 결과를 별도 읽기 전용 진단
어댑터에 연결하는 작업**이다. 기능별 수동 테스트를 반복하지 않고,
안전한 자동 테스트/진단 자료 기반으로 먼저 검증해야 한다.
